# 本番コード規約

このディレクトリのコードは運用される。実験コード規約は適用されない。

**実験コードをコピーして持ち込まない。** アルゴリズム設計書（`docs/design/`）を参照し、本規約に沿って書き直すこと。

実装の進め方は `.claude/rules/testing.md`（テストファースト）に従う。

## 1. 設計書との整合

- 実装前に該当するアルゴリズム設計書・システム設計書を必ず読む
- **設計書に定義が無い挙動を推測で実装しない**。手を止めて確認する
- 設計書と異なる実装が必要になった場合、実装を進める前に報告する
- 設計書の「実験からの差分」に記載が無い差分を新たに作らない

## 2. ハードコーディングの禁止

- パス、閾値、ハイパーパラメータ、期間、カラム名を直接書かない
- 設定ファイルまたは定数モジュールへ外出しする
- マジックナンバーには必ず名前を付ける

## 3. 型と構造

- 関数の引数と戻り値に型ヒントを必ず付与する
- 複雑な辞書を返さない。`dataclass` / `TypedDict` / Pydantic モデルでデータ構造を明示する
- 外部から流入するデータ（ファイル、API、DB）はスキーマ検証を通してから処理する

## 4. 前処理の fit / transform 分離

**実験から本番への移行で最も壊れやすい箇所。**

- 学習データから統計量を学習する処理（スケーラ、補完値、エンコーダ、外れ値閾値、次元削減）は、fit と transform を明確に分離する
- 推論経路で fit を呼ばない。学習済みオブジェクトを読み込んで transform のみ実行する
- 学習済み前処理オブジェクトはモデルと**対で保存**し、バージョンの対応関係をメタデータに残す
- 前処理の適用順序は設計書の記載と一致させる。順序を変えない

## 5. 例外・境界処理

設計書の例外処理表に従い、以下すべてに明示的な挙動を実装する。未定義のまま放置しない。

- 学習時に存在しなかったカテゴリ値
- 特徴量の欠損
- 学習時の値域を外れる入力
- 履歴不足（コールドスタート）
- 入力データの取得失敗
- 推論処理の失敗

「例外を送出する」も正当な実装だが、**黙って既定値で埋めることは禁止**する。予測が静かに劣化する。

## 6. 副作用の分離

- I/O（ファイル・DB・API）と計算ロジックを同一関数に混ぜない
- 計算ロジックは入力に対して決定的な関数として書き、単体でテスト可能にする
- 乱数を使う箇所はシードを引数または設定で受け取る。関数内で暗黙に初期化しない

## 7. ログ

- `print()` を使わない。`logging` を使用する
- モジュールレベルで `logger = logging.getLogger(__name__)` を定義する
- 進捗・結果は `info`、想定内の異常は `warning`、処理継続不能は `error`
- **入力データの実値・予測対象の識別子をログに出力しない**（機密データ規約）
- 件数・分布・処理時間など、監視に使える統計量は積極的に出力する

## 8. エラー処理

- `except Exception: pass` を禁止する
- 捕捉する例外は具体的なクラスを指定する
- 記録してから再送出するか、スキップ理由を明示的にログへ残す
- 認証情報・入力データの実値が例外メッセージ経由で漏れないようにする

## 9. 外部API呼び出し

- リトライ（Exponential Backoff）とタイムアウトを必ず実装する
- 失敗時の方針（中断 / フェイルソフト）を設計書に沿って実装し、コメントに根拠を残す

## 10. LLMプロンプトをコード内で組み立てる場合

- データと指示の境界をXMLタグで明示する（`<data>...</data>`）
- フォーマット例は `<format_example>...</format_example>` で分離する
- データをプロンプト末尾に連結するだけの実装を禁止する

## 11. 実験との一致

実装完了後、設計書の「実験との一致確認項目」に基づき `algorithm-verifier` エージェントで検証する。
**自己申告で「実験どおり実装した」と結論づけない。**
