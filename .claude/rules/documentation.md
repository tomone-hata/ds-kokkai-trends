# ドキュメント運用規約

適用範囲: `docs/` 配下の全ファイル。索引は `CLAUDE.md` 7章。

## 0. 大原則

1. **`docs/` 配下は全て公開可能なものに限る。** 発言本文・生レスポンス・機密データを置かない。公開できないものは `private/` に置き、`docs/` からはパスで参照する。**判断に迷ったら `private/` へ置く**
2. **会話の経緯を前提に書かない。** セッションをまたぐとコンテキストは失われる。「先ほどの件」「例のモデル」のような書き方を禁止し、**各文書は単体で内容が復元できるように書く**
3. **文書を追加・改訂・廃止したら `docs/INDEX.md` を更新する。** 目録に載っていない文書は存在しないものとして扱う
4. **廃止した文書を削除せず「廃止」と明記する。** 過去の判断の経緯を残すため

### 公開・非公開の境界

| ディレクトリ | Git | 置くもの |
|---|---|---|
| `docs/` | 追跡 | 全ての文書。公開可能なものに限る |
| `docs/inputs/` | 追跡 | **外部から得た一次情報**（3.6節）。`docs/` 配下のため公開可能なものに限る。追記のみ |
| `data/` | 対象外 | 生データ・中間生成物・データセット |
| `outputs/` | 対象外 | 実験・分析の全出力（`README.md` のみ追跡） |
| `private/` | 対象外 | 調査用の機密データ、非公開の証跡（`README.md` のみ追跡） |

`private/` の内容は他の環境に存在しない。**`docs/` 側の文書は、証跡が無くても内容が追えるだけの情報を本文に持たせること。**

### `docs/` に書いてよいデータの粒度

**国会会議録APIから取得したデータは機密扱い**（`CLAUDE.md` 3章）。出典が公開情報であることを理由に緩めない。

| 区分 | 該当するもの | 記載 |
|---|---|---|
| 生の発言と話者 | 発言本文、発言者名、`speechID` / `issueID` | **禁止**（引用も不可） |
| 集計軸 | 開催日、院名、会議名、国会回次、号数、所属会派、肩書き | 集計した形でのみ可 |
| 集計値 | 件数、統計値、クラスタ数・サイズ、時系列の推移、クラスタの特徴語 | 可 |

**集計軸を個票と結びつけて書かない。** 単独では個人を指さない値でも、組み合わせると特定できる（例: 開催日＋肩書き）。
**クラスタの特徴語に個人名が現れた場合は伏せる**（「議員A」）。具体例が必要な場合はダミーデータを使い「※ ダミーデータです」と明記する。

## 1. 3つの入口

| ファイル | 役割 | 更新頻度 |
|---|---|---|
| `docs/PROJECT_STATUS.md` | **いま何をしているか**（フェーズ・ブロッカー・直近の決定） | 都度 |
| `docs/INDEX.md` | **何が存在するか**（全文書の目録・版数・状態） | 文書の増減時 |
| `docs/CHANGELOG.md` | **何をどう変えてきたか**（更新履歴） | 作業の区切りごと |

**判断根拠を `PROJECT_STATUS.md` に書かない。** ADRを起こしてリンクする。

### 更新履歴の書き方

1. **同じ日・同じ対象の変更は、最終状態のみを1行で書く。** AをBにし、さらにBをCにしたなら「AをCにした」と書く。途中経過を残すと現在の状態が読み取れなくなるため
2. **対象が異なれば、同じ日でも行を分ける。** 「クラスタリングの実験」と「API取得仕様の変更」をまとめない。正規化するのは対象が同じ場合に限る
3. **過去の日付の記述は書き換えない。** 正規化してよいのは当日の作業中のみ。**例外は、誤って別の日付のセクションに書かれた記述を正しい日付へ移す場合に限る**（内容の書き換えは行わない）。この例外がないと、日付をまたいだ誤記載を永久に訂正できなくなるため
4. **コミット単位の機械的な記録はgitに任せ、ここには判断と結果を書く。** 「なぜ」が要る場合はADRを起こしてリンクする

## 2. ID体系

| 接頭辞 | 対象 | 置き場所 |
|---|---|---|
| `EXP-NNN` | 実験 | `docs/experiments/EXP-NNN-{slug}/` |
| `ISSUE-NNN` | 課題・不具合 | `docs/issues/ISSUE-NNN-{slug}/` |
| `ADR-NNN` | 決定記録 | `docs/decisions/ADR-NNN-{slug}.md` |

番号は種別ごとの通し番号（フェーズで区切らない）。欠番を埋め直さない。

**実験は、ドキュメント側 `docs/experiments/EXP-NNN-{slug}/` と実コード側 `experiments/EXP-NNN-{slug}/` でディレクトリ名を一致させる。** IDで双方向に辿るため。

## 3. 4つのフロー

| 起点 | 流れ | `drafts/` を経由 |
|---|---|---|
| 新規設計・新規要件定義 | `drafts/` で執筆 → レビュー → **確定先**（設計書は `design/`、要件定義書は `requirements/`）へ移動、v1.0 | ○ |
| 技術選定・方針変更 | `ADR-NNN` で決定 → 影響する `design/` 文書を改訂、版up | ✗ |
| 不具合 | `ISSUE-NNN` 起票 → 調査ログ → 原因特定 → 対策 | ✗ |
| 外部仕様変更（NDL API等） | `ISSUE-NNN`（種別: 外部要因）→ 影響調査 → `design/` 改訂 | ✗ |

**`drafts/` は確定版がまだ存在しない新規文書に限る。** 既存文書の改訂で `drafts/` にコピーを作ると確定版と二重管理になり、必ず乖離するため。

## 3.5 ブランチ運用（ADR-003）

作業はブランチを切って行う。**`main` へ直接コミットしない。**

**マージは必ず Pull Request 経由で行う。ローカルでの `git merge` による `main` への統合を禁止する**（ADR-005）。

- 手順: ブランチを push → PR 作成 → 差分を確認 → GitHub 上でマージ
- マージ方法は **Merge commit** に固定する（Squash / Rebase を使わない）。作業の単位を履歴に残すため
- 単独開発でもPRを経由する。**差分を一覧で確認する強制力そのものが目的である**
- 長命ブランチが `main` を取り込む方向（`git merge main`）はローカルで行ってよい。`main` の状態を変えないため

| 種別 | ブランチ名 | マージの条件 |
|---|---|---|
| 実験 | `exp/EXP-NNN-{slug}` | `plan.md` と `report.md` が揃っている |
| 課題・不具合 | `issue/ISSUE-NNN-{slug}` | `issue.md` が「対応済」または「仕様として受容」 |
| 決定・設計改訂 | `adr/ADR-NNN-{slug}` | 影響する文書の改訂履歴が更新されている |
| 実装 | `feat/{slug}` | テストが通る |
| 新規文書の作成 | `docs/{slug}` | `INDEX.md` に登録され、`drafts/` から確定先へ移動している |
| フェーズ単位の作業 | `poc/{slug}` など | 当該フェーズの成果物が揃い、レビュー判定が出ている |

**フェーズ単位のブランチは、複数の成果物を1本にまとめる場合に使う。** 個別の `docs/` や `exp/` を別途切らず、フェーズ完了時に一括でマージする。長命になるため `main` を定期的に取り込むこと。

### 規約自体の変更（ADR-004）

**規約の変更もブランチを経由する。`main` への直接コミットは行わない。例外は設けない。**

どのブランチに載せるかは**影響範囲**で判断する。

| 影響範囲 | 載せるブランチ |
|---|---|
| その作業に閉じる（特定の実験・開発の過程で判明し、他の進行中の作業に影響しない） | **その実験・開発のブランチに含める。** 専用ブランチを切らない |
| 他の作業にも及ぶ（全体の運用方法、複数ブランチが従う規則） | **規約配信用のブランチを切り**、`main` へ速やかにマージする |

判断に迷う場合は専用ブランチを切る。マージが早ければコストは小さい。

**規約の効力は決定した時点から生じ、そのファイルがどのブランチに存在するかとは独立である。** ファイルの所在と規約の効力を混同しない。

実験ブランチは **`plan.md` を書く時点で切る**。実施前に計画を確定させる規約（5節）と対応させるため。
**結果がNo-Goの実験もマージする。** 失敗した実験ほど記録価値が高い。

マージ前に `INDEX.md` と `CHANGELOG.md` を更新すること。

### マージ後はブランチを削除する（削除は承認を得てから）

**マージが完了したブランチは、リモート・ローカルとも削除する。ただし自動で削除しない。**

| 手順 | 実行者 |
|---|---|
| 1. マージ後、削除対象のブランチを一覧で提示する | 担当（定型作業として必ず行う） |
| 2. 削除してよいかを確認する | 担当 |
| 3. 承認を得てからリモート・ローカルの順に削除する | 担当 |

**提案は定型で行い、実行は承認を得てから行う。** 削除し忘れて積み上がることも、確認なく消えることも防ぐため。

```bash
git push origin --delete <branch>   # リモート
git branch -d <branch>              # ローカル（未マージなら失敗するため安全）
git remote prune origin             # 削除済みリモート追跡の掃除
```

削除はリモートまで消すと復旧にコミットハッシュの特定を要し、取り消しに手間がかかる。また「マージ済み」の判定を誤れば作業を失う。`CLAUDE.md` 5章「Git操作はユーザーから明示的な指示がある場合のみ実行する」を、本操作について具体化したものである。

**削除してもマージコミットが履歴に残るため、作業の記録は失われない。** [ADR-003](../../docs/decisions/ADR-003-branch-strategy.md) が「実験も成果物として残す」と定めるのはコミットとファイルについてであり、**ブランチ参照を残すこととは別である。**

削除しないとマージ済みブランチが際限なく積み上がり、`git branch` の出力から**現在進行中の作業が判別できなくなる。**

`git branch -d`（小文字）を使うこと。未マージのブランチでは失敗するため、誤って作業中のブランチを消す事故を防げる。強制削除（`-D`）は、破棄すると決めたブランチにのみ用いる。

## 3.6 上流の入力（`docs/inputs/`）

外部から得た一次情報の置き場。**私たちが書いた文書ではなく、判断の根拠となった事実を記録する。**

| 対象 | 例 |
|---|---|
| ヒアリング記録 | 依頼者との対話で確定した要件、未確定事項への回答 |
| 参照データ | 評価に用いる参照論点リストなど、公開情報から抽出したもの |

**評価や比較に用いる参照データは、可能な限り評価対象データとは独立した公開ソースから作成する**（ADR-006）。独立したソースが存在せず、評価対象データそのものから作成せざるを得ない場合は `private/` へ置く。**抽象度の類推によって `docs/` へ置かない。**

**`docs/inputs/` は追記のみ。後の決定に合わせて書き換えない。**

これが最重要のルールである。記録を事後に編集できると、**それを根拠とする `[事実]` タグの検証が循環して無意味になる。** 認識が変わった場合は記録を修正せず、後日の記録を新たに追加する。対話の中で前言が修正された場合も、修正前の内容を削除せず残す。

ヒアリング記録では、**依頼者自身の発言と、こちらの提案に対する承認とを区別して記録する。** 前者は要件定義書の `[事実]` の根拠となるが、後者は案の内容がこちら由来であるため `[推測]` に近い。この区別がないとタグ付けの妥当性を検証できない。

`requirements/` に混ぜない。確定した要件と、その入力である記録が判別できなくなるため。

## 4. 確定文書の改訂

`docs/design/` と `docs/requirements/` に置くのは確定版のみ。**実装が参照してよいのはこれらの「現役」文書だけ**（`CLAUDE.md` 2章の原則1）。

1. **改訂は作業ブランチ上で行い、マージをもって確定とする。** `main` 上の確定先が常に確定版である状態を保つ
2. **確定後の改訂には必ず `ISSUE-NNN` または `ADR-NNN` の起票を先行させる。** 「なぜこの仕様なのか」を文書単体から辿れるようにするため
3. **改訂履歴を文書内の表に残す**（版・日付・変更内容・起票ID）
4. 版数は、方式・スキーマ・インタフェースの変更でメジャー、記述の補足・誤記の修正でマイナーを上げる

### 確定前のドラフト改訂に起票は要しない

2の起票義務は**確定後の改訂に対するもの**であり、`drafts/` 上でv1.0に至るまでの改訂には適用しない。
確定前の改訂は仕様の変更ではなく仕様の形成であり、「確定した仕様がなぜ変わったか」という問いが成立しないため。
ただし**変更理由は追跡可能でなければならない。** ヒアリング記録（`docs/inputs/`）またはレビューレポート（`docs/reviews/`）のいずれかを改訂履歴の起票列に記載すること。どちらにも根拠がない改訂は行わない。

### フェーズ単位ブランチ上の確定文書の扱い

フェーズ単位ブランチ（`poc/{slug}` 等）は長命であり、その上でv1.0に達した文書は**マージまで `main` に現れない。**

このとき文書の状態欄には **「現役（`{ブランチ名}` 上。`main` へのマージをもって確定）」** と記載する。ブランチ上でのみ確定していることを明示するため。

**成果物ごとに先行してマージしない。** `main` へマージしてよいのは完了した単位のみである。
フェーズの途中にある成果物を個別に出せるようにすると、他の実験や改修も同じ理由で出せることになり、**`main` が未完成品を含む状態を許容することになる。**
規約の変更が専用ブランチで先に出せるのは（[ADR-004](../../docs/decisions/ADR-004-rule-change-via-branch.md)）、規約変更それ自体が完結した単位だからであり、フェーズの一部だからではない。

## 5. 実験

1実験につき3箇所を、**同一のディレクトリ名**で対応させる。

| 場所 | 内容 | Git |
|---|---|---|
| `docs/experiments/EXP-NNN-{slug}/` | `plan.md`・`report.md`・`figures/` | 追跡 |
| `experiments/EXP-NNN-{slug}/` | 実験コード（`run.py`・`config.md`） | 追跡 |
| `outputs/EXP-NNN-{slug}/` | 全出力 | 対象外 |

- **`plan.md` は実験の実施前に書き、実施後に書き換えない。** 結果を見てから計画を書き直せると撤退基準が意味を失うため（`CLAUDE.md` 2章の原則3と同じ思想）
- **想定と異なる結果が出た場合は `report.md` に差分として記録する。** ここが次の実験の起点になる
- 撤退基準を実施後に緩めない
- 図は `outputs/` に全て吐き、**レポートに採用したものだけを `docs/.../figures/` へコピーする**
- **図に発言本文を焼き込まない。** ラベルには特徴語・クラスタIDを使う

## 6. 課題・不具合

`docs/issues/ISSUE-NNN-{slug}/issue.md` に本体を置く。台帳は `docs/issues/README.md`。

- 種別は **不具合 / 外部要因 / 改善 / 調査**
- **調査ログは追記のみ。否定された仮説も消さない。** 同じ調査を繰り返さないための記録である
- 原因が未特定なら「未特定」と書き、状態を「調査中」のままにする。空欄で放置しない
- 対策がコード修正のみで済む場合は ISSUE 内で完結させ、`design/` は触らない。設計変更を伴う場合のみ4節の改訂フローに接続する

### 証跡の置き分け

| 種別 | 置き場所 | 例 |
|---|---|---|
| 公開可能 | `docs/issues/ISSUE-NNN-{slug}/` 直下 | エラーメッセージ、本文を除いたレスポンス構造、件数・統計値、再現スクリプト |
| 非公開 | `private/issues/ISSUE-NNN-{slug}/` | 生レスポンス、詳細ログ、目視確認用に抜き出した個票 |

**非公開側の中身を `docs/` に転記しない。** `issue.md` にはパスと内容の説明だけを書き、必要なら公開可能な形に加工して本文へ載せる。
**`speechID` を伏せずに書かない**（`xxxxxxxxxxxxxxxxxxxxx_NNN` のように伏せる）。

## 7. 決定記録（ADR）

`docs/decisions/ADR-NNN-{slug}.md`。

- **ADRは追記のみ。決定を覆す場合、既存のADRを書き換えず新しいADRを起こし、旧ADRを「棄却（ADR-NNNにより）」にする**
- **決定は維持したまま根拠のみを訂正する場合は、新ADRを起こさず「訂正（YYYY-MM-DD）」節を追記する。** 本文の該当箇所は書き換えず、どの根拠が誤りでありなぜ結論が変わらないかを明示する。決定の変更と根拠の訂正を混同しないため
- **「見直す条件」を必ず書く。** どうなったら再検討するかを期限か閾値で示す
- 推測と実測を区別する。実測値がある場合は必ず記載する

## 8. テンプレート

`docs/_templates/` から複製して使う。

| ファイル | 用途 |
|---|---|
| `experiment-plan.md` | 実験計画書 |
| `experiment-report.md` | 実験レポート |
| `issue.md` | 課題・不具合 |
| `adr.md` | 決定記録 |
| `design-doc.md` | 設計書・仕様書 |
