# テスト規約

## 1. テストファースト

**テストを書いてから実装する。この順序を逆にしない。**

理由: 実装後にテストを書くと、テストは「実装が実際にやったこと」を追認するだけになり、設計書で定義された仕様が検証されないまま消える。特に例外処理・境界条件は、実装で考慮漏れがあるとテストからも同時に漏れる。

### 手順

1. **設計書を読む** — アルゴリズム設計書の受入条件・例外処理表・検証計画、および要件定義書の受入条件
2. **テストケースを列挙し、ユーザーに提示する** — 実装前に、何を検証するかの合意を取る。設計書の例外処理表の各行が、最低1つのテストケースに対応していること
3. **テストを書き、失敗することを確認する** — 実装が無い状態で通るテストは、何も検証していない
4. **実装する**
5. **テストを通す**

### 禁止事項（最重要）

- **テストが失敗したとき、テストの側を実装に合わせて書き換えない**
- 期待値を実装の出力で上書きしない。「実行結果をコピーして期待値にする」を禁止する
- テストが誤っていると考える場合は、**設計書に照らして判断し、テストを変更する前にユーザーに報告する**
- 通らないテストを skip / xfail で回避しない。回避する場合は理由と解消予定を明記する

この規約が守られない場合、テストは設計の検証ではなく実装の追認になり、存在価値を失う。

### 適用範囲

適用するのは `src/` `scripts/` の決定的なロジックすべて（前処理、特徴量算出、検証、分岐、I/O境界、後処理）。

**適用しないもの**: モデルの精度そのもの。「AUCが0.75以上」は事前にテストとして書けない。精度は `experiment-analyst` が実験段階で判定し、実装が実験を再現しているかは照合用データセットを使ったゴールデンテストで担保する。

探索的に挙動を確認したい場合は `experiments/` で行い、結果が固まってから持ち込む。

## 2. テスト観点

新規実装・修正時に以下を走査し、該当する観点のテストを用意する。該当しない観点は「対象外」と判断した理由を持つこと。

### 汎用観点

| 観点 | 内容 |
|---|---|
| **正常系** | 想定通りの入力に対して、期待する出力・型・構造になることを確認する |
| **異常系** | 不正な入力、欠損値、空データ、型違い、存在しないファイルなどで適切に例外・エラー処理されることを確認する |
| **境界値** | 空文字、0件、1件、大量データ、最大・最小値、閾値ちょうどなどを確認する |
| **設定値の読み込み** | config、環境変数、定数、デフォルト値が正しく反映されることを確認する |
| **データ変換** | 入力データが期待した形式・列名・型・値に変換されることを確認する |
| **分岐条件** | if文、条件分岐、フラグ、モード切替ごとの挙動を確認する |
| **副作用の確認** | ファイル出力、ログ出力、ディレクトリ作成などが期待通り行われることを確認する |
| **副作用の抑制** | 外部API、LLM、DB、本番ファイル、ネットワークにはアクセスしない。必要ならmockする |
| **回帰テスト** | 過去に発生したバグと同じ条件をテスト化し、再発を検知できるようにする |
| **再現性** | 乱数、時刻、LLM出力など非決定的な処理は固定化・mock化する |
| **機密情報の排除** | 実データ、顧客情報、APIキー、実データのテキストなどをテストに含めない |
| **小さな単位で検証** | 1つのテストでは1つの関心事だけを確認し、失敗原因が分かるようにする |
| **期待値を明示** | 「エラーにならない」だけでなく、戻り値・列・件数・値を具体的に検証する |
| **読みやすさ** | Arrange / Act / Assert の形で、入力・実行・検証を分けて書く |
| **実行速度** | テストは軽量にし、通常開発時にすぐ実行できる範囲にする |

### 機械学習固有の観点

| 観点 | 内容 |
|---|---|
| **スキーマ整合** | 入出力の列名・型・列順が設計書の定義と一致することを確認する。列順に依存する処理は特に明示的に検証する |
| **fit / transform の分離** | 推論経路で fit 系の処理が呼ばれないことを確認する。学習済みオブジェクトを与えずに推論を実行したら失敗すること |
| **リーケージ防止** | 分割前に統計量を学習していないこと、評価データが学習に混入していないことを構造的に検証する |
| **時系列の順序** | 時系列分割で学習側に未来のレコードが含まれないことを確認する |
| **グループの非跨り** | 同一エンティティが学習側と評価側の双方に出現しないことを確認する |
| **例外系の網羅** | 設計書の例外処理表の各行（未知カテゴリ、欠損、値域外、履歴不足、取得失敗）に1対1でテストを対応させる |
| **既定値での穴埋め禁止の検証** | 想定外入力が黙って既定値に置き換わっていないことを確認する |
| **決定性** | 同一入力・同一シードで出力が完全に一致することを確認する |
| **ゴールデンテスト** | 設計書の照合用データセットに対する期待出力を固定し、実装変更による数値の変化を検知する |
| **数値比較の許容誤差** | 浮動小数点は完全一致を要求せず、設計書に定義された許容誤差で比較する。許容誤差が未定義なら設計書へ差し戻す |
| **モデル成果物の整合** | モデルと前処理オブジェクトのバージョンが不整合な場合にロードが失敗することを確認する |

## 3. テストの構成

```
tests/
  unit/          外部依存なし・高速。開発中に常時実行する
  integration/   DB・ファイルI/Oを含む
  golden/        照合用データセットによる数値再現テスト
  fixtures/      ダミーデータ（実データを置かない）
```

- 外部API・LLMを呼ぶテストは既定の実行対象から外し、明示的に指定したときのみ実行する
- フィクスチャには実データを使わない。構造を模したダミーデータを生成する
- テスト名は「何を検証しているか」が読めるものにする
