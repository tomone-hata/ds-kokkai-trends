# ADR-002: 公開・非公開の境界をディレクトリで分け、`docs/` は全て公開可能とする

| 項目 | 内容 |
|---|---|
| ID | ADR-002 |
| 状態 | 採用 |
| 決定日 | 2026-08-18 |
| 関連 | `CLAUDE.md` 2章の原則7・3章、`.claude/rules/documentation.md` |

## 1. 背景

課題・決定記録・実験レポートはGitHubへ公開して差し支えない一方、収集した発言本文は著作権が個々の発言者に帰属し、公開（公衆送信）できない。
当初は不具合の証跡を `docs/issues/*/evidence/` に置く設計だったが、これは公開可能な文書と公開できないデータを同じ階層に混在させるものであった。

機密データがGitの履歴に一度入ると、後から剥がすのは履歴の書き換えを要し極めて厄介である。**境界は構築時点で引く必要がある。**

さらに本プロジェクトは、顧客アンケートの自由記述や社内機密データを扱う案件の進め方を検証する場も兼ねている。
それらの案件で自由記述の実データが置かれる位置は、本プロジェクトの発言本文と同一である。**この境界設計はそのまま転用できることを要件とする。**

## 2. 決定

**`docs/` 配下には公開可能なものだけを置く。** 公開できないものは `private/` に置き、`docs/` からはパスで参照する。判断に迷う場合は `private/` へ置く。

**国会会議録APIから取得したデータは機密データとして扱う。** 出典が公開情報であることを理由に緩めない。

境界は「**生の発言と話者を出さない**」に置く。

| 区分 | 該当するもの | `docs/` への記載 |
|---|---|---|
| 生の発言と話者 | 発言本文、発言者名、`speechID` / `issueID` | 禁止（引用も不可） |
| 集計軸 | 開催日、院名、会議名、国会回次、号数、所属会派、肩書き | 集計した形でのみ可 |
| 集計値 | 件数、統計値、クラスタ数・サイズ、時系列の推移、特徴語 | 可 |

所属会派・肩書き・会議名を集計軸側に置くのは、これらが**話者そのものではなく、分析の主要な軸**であるため。
実務上も、組織区分（部門・拠点）を機密として扱う例は多くない。一方で**集計軸を個票と結びつけて書くことは禁じる** — 単独では個人を指さない値でも、組み合わせると特定できる（例: 開催日＋肩書き）。

`docs/issues/*/evidence/` は廃止する。

## 3. 検討した選択肢

| 案 | 内容 | 採否 |
|---|---|---|
| A | ディレクトリで公開・非公開を分ける | **採用** |
| B | `docs/` 内に置いたまま、ファイル単位で `.gitignore` に列挙する | 不採用 |
| C | リポジトリをprivateにし、境界を設けない | 不採用 |

## 4. 判断根拠

1. **境界が構造として見える。** ディレクトリを見れば公開可否が判断でき、判断を毎回行わずに済む
2. **事故が起きにくい。** ファイル単位の除外（案B）は、新規ファイルを作るたびに `.gitignore` への追加が必要で、追加漏れがそのまま漏洩になる。ディレクトリ単位なら既定で除外される
3. **他案件へ転用できる。** 顧客アンケートの自由記述、社内機密データを扱う場合も同じ構造で運用できる
4. **publicに耐える制約を既定とする方が安全側。** privateリポジトリを前提に緩めた運用は、公開の判断が出た時点で破綻する。逆方向（厳しく作って後で緩める）は履歴を汚さない
5. **取得データを機密扱いにするのは、手順の検証を成立させるため。** 国会会議録は出典としては公開情報だが、ここで緩めると本番想定（顧客アンケートの自由記述・社内機密データ）と手順が変わってしまい、予行演習として機能しない。データの性質ではなく**運用手順を揃えること**を優先する

## 5. 採用しなかった案を退けた理由

- **案B**: 除外の追加漏れが直接漏洩につながる。個人開発でレビュー者が自分しかいない状況では、この失敗モードを構造で防ぐべき
- **案C**: リポジトリのpublic化を将来の選択肢として残せなくなる。また、機密データを扱う案件の予行演習という目的を満たさない

## 6. 想定される結果

| 良い影響 | 悪い影響・受け入れるコスト |
|---|---|
| 公開可否の判断が構造で決まり、事故が起きにくい | 証跡が2箇所に分かれ、参照にひと手間かかる |
| 他案件へそのまま転用できる | `private/` の内容は他環境に存在せず、共有できない |

**`private/` が他環境に存在しない**ことへの対策として、`docs/` 側の文書は証跡が無くても内容が追えるだけの情報を本文に持たせることを規約とする（`.claude/rules/documentation.md` 0節）。

## 7. 見直す条件

- **議員ごとのトレンド分析を要件に加える段階**。発言者名を分析軸として扱う必要が生じるため、話者の扱いを再検討する。**その場合も「生の発言（発言本文）を載せない」は維持する方向で検討すること**
- 複数人での開発になり、`private/` の内容を共有する必要が生じたとき（別の共有手段を検討する）
- 本プロジェクトを非公開運用に確定し、かつ転用の想定を取り下げたとき
