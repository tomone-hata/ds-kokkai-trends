# ADR-003: 実験・課題・実装をブランチで分け、実験も成果物として同一リポジトリに残す

| 項目 | 内容 |
|---|---|
| ID | ADR-003 |
| 状態 | 採用 |
| 決定日 | 2026-08-18 |
| 関連 | `CLAUDE.md` 5章、`.claude/rules/experiment-code.md`、`.claude/rules/documentation.md` |

## 1. 背景

PoCは一度の実験では完了せず、条件を変えた実験を繰り返すことが見込まれる。
また[ADR-002](ADR-002-public-private-boundary.md)で定めた確定文書の改訂フローは、作業ブランチ上での編集を前提としている。

作業単位の切り方と、実験コードを最終的にどう扱うかを決める必要があった。

## 2. 決定

**作業はブランチを切って行い、完了時に `main` へマージする。`main` へ直接コミットしない。**

**実験も成果物として定義し、本番コードと同一リポジトリに残す。** 実験用の別リポジトリを作らない。

| 種別 | ブランチ名 | マージの条件 |
|---|---|---|
| 実験 | `exp/EXP-NNN-{slug}` | `plan.md` と `report.md` が揃っている |
| 課題・不具合 | `issue/ISSUE-NNN-{slug}` | `issue.md` の状態が「対応済」または「仕様として受容」 |
| 決定・設計改訂 | `adr/ADR-NNN-{slug}` | 影響する文書の改訂履歴が更新されている |
| 実装 | `feat/{slug}` | テストが通る |

マージは `--no-ff` で行い、作業の単位を履歴に残す。

> **[ADR-005](ADR-005-merge-via-pull-request.md) による改訂（2026-08-18）**: ローカルでの `git merge` は禁止し、**Pull Request 経由でマージする**。
> マージ方法は Merge commit（`--no-ff` 相当）に固定し、Squash / Rebase を使わない。作業の単位を履歴に残すという本ADRの意図は維持される。

**結果がNo-Goの実験もマージする。** 失敗した実験ほど記録価値が高い。

### 発効点

**本ADRを導入するコミット自体は `main` への直接コミットとする。** 規約が存在しない時点の作業にその規約を適用できないため。
このコミット以降のすべての作業にブランチ運用を適用する。

### 補足（2026-08-18 追記）

当初の表に、**新規文書の作成**と**フェーズ単位のまとまった作業**に対応する種別が欠けていた。以下を追加する。

| 種別 | ブランチ名 | マージの条件 |
|---|---|---|
| 新規文書の作成 | `docs/{slug}` | `INDEX.md` に登録され、`drafts/` から `design/` または `requirements/` へ移動している |
| フェーズ単位の作業 | `poc/{slug}` など | 当該フェーズの成果物が揃い、レビュー判定が出ている |

**フェーズ単位のブランチは、複数の成果物（要件定義書・設計書・実験）を1本にまとめる場合に使う。**
この場合、個別の `docs/` や `exp/` ブランチを別途切らず、フェーズ完了時に一括でマージする。
ブランチが長命になるため、`main` から乖離しないよう定期的に取り込むこと。

### ~~例外: 規約自体の変更は `main` へ直接コミットしてよい~~ （廃止）

> **本例外は [ADR-004](ADR-004-rule-change-via-branch.md) により廃止された（2026-08-18）。**
> 規約の変更もブランチを経由する。`main` への直接コミットは行わない。
> どのブランチに載せるかは影響範囲で判断する（その作業に閉じるなら当該ブランチ、他へ及ぶなら規約配信用ブランチ）。
> 以下は廃止時点の記述を経緯として残すものであり、**適用しない**。

対象は `CLAUDE.md`、`.claude/rules/`、および本ADRのような運用ルールを定める文書。

規約はすべてのブランチへ即時に適用されるべきものであり、ブランチに閉じ込めると、
マージされるまでの間、並行する作業が古い規約のまま進んでしまう。長命なフェーズブランチがある場合に特に問題となる。

**成果物（要件定義書・設計書・実験・実装）の変更にこの例外を適用しない。**

## 3. 検討した選択肢

| 案 | 内容 | 採否 |
|---|---|---|
| A | 単一リポジトリでブランチ分割。実験も成果物として残す | **採用** |
| B | 実験用リポジトリと本番リポジトリを分離 | 不採用 |
| C | `main` に直接コミットし、ブランチを使わない | 不採用 |

## 4. 判断根拠

1. **AI開発では実験そのものが成果物である。** 何を試して何が駄目だったかは、モデルの精度と同等に重要な資産であり、本番コードと切り離すと参照されなくなる
2. **既存規約と整合する。** `experiment-code.md` はすでに「失敗した実験のディレクトリも削除しない（同じ失敗を繰り返さないため）」と定めており、実験を残す前提になっている
3. **依存方向が一方向に固定されているため、混在しても本番が汚染されない。** `experiments/` は `src/` を import してよいが逆は禁止（`experiment-code.md`）。この制約がある限り、同居のコストは低い
4. **ID体系がそのままブランチ名になる。** `EXP-NNN` / `ISSUE-NNN` / `ADR-NNN` とブランチが1対1で対応し、履歴と文書が相互に辿れる
5. **確定文書の改訂フローがブランチを前提としている**（[ADR-002](ADR-002-public-private-boundary.md)）。実験だけ別の運用にすると規約が二重になる

## 5. 採用しなかった案を退けた理由

- **案B**: リポジトリを分けると、実験結果と本番実装の対応が人手の管理になる。「この実装はどの実験に基づくか」を辿れなくなり、`CLAUDE.md` 2章の原則1（設計書との整合）を検証できない
- **案C**: 実験の途中経過が `main` に混ざり、どこまでが確定した状態か判別できなくなる。ADR-002の「`main` 上の `design/` は常に確定版」が成立しない

## 6. 想定される結果

| 良い影響 | 悪い影響・受け入れるコスト |
|---|---|
| 実験・課題・実装が履歴上で1つの塊として見える | ブランチ操作の手数が増える |
| 失敗した実験が資産として残る | リポジトリのサイズが単調増加する |
| 実装から根拠となる実験へ辿れる | 実験コードの品質が本番と混同されるリスク |

最後のリスクへの対策として、`experiments/` は「使い捨て・ハードコード可」、`src/` は「ハードコード禁止・テストファースト」と規約を分離済み（`CLAUDE.md` 1章）。
**実験コードを本番へコピーせず、アルゴリズム設計書を経由して書き直す**（`CLAUDE.md` 2章の原則4）。

## 7. 見直す条件

- リポジトリのサイズが実用上の支障になったとき（実験の出力は `outputs/` でGit管理外のため、当面は想定しにくい）
- 複数人が並行して実験を行い、ブランチが恒常的に競合するようになったとき
