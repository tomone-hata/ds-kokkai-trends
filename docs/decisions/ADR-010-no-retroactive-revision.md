# ADR-010: 規約変更を過去へ遡って適用しない。実害が出る場合のみ個別に見直す

> **ADRは追記のみ。決定を覆す場合、この文書を書き換えず新しいADRを起こして本文書を「棄却」にする。**
> 過去の判断の経緯を残すことが目的であるため。
> 会話の経緯を前提にせず、この文書単体で判断が追えるように書くこと。

## 1. 背景

### ADR-004 が定めていない領域

[ADR-004](ADR-004-rule-change-via-branch.md) は**規約変更をどのブランチで配信するか**を定め、「規約の効力は決定した時点から生じ、そのファイルがどのブランチに存在するかとは独立である」と述べている。

**しかし、規約変更以前に書かれた確定文書やコードをどう扱うかは定めていない。**

`CLAUDE.md` 2章の原則6 は「**規約が変更されても既存コードを自動修正しない。** 新規コードと明示的に依頼されたコードにのみ適用する」と定めており、コードについては答えがある。**確定文書（`docs/design/`・`docs/requirements/`）についての規定が無い。**

### 実際に判断を迫られた

[ADR-009](ADR-009-dependency-declaration.md)（依存の完全固定）を決定した際、PoC設計書 17章に次の記述があった。

> 依存の追加は `uv add {package}` で行う（`pip install` を使わない、`CLAUDE.md` 6章）

**この記述は書かれた時点では正しい。** 当時の `CLAUDE.md` 6章がそう定めており、それを引用していたにすぎない。

しかし放置すると `CLAUDE.md` 2章の原則1（**設計書と整合しない実装を行わない**）と衝突する。**実装が設計書に従うことで規約違反になる。**

このとき「設計書が間違っているので直す」と判断しかけたが、**それは書かれた時点の判断を否定する言い方である。**

## 2. 決定

**規約変更を過去へ遡って適用しない。旧規約下で書かれた文書・コードを「誤り」として扱わない。**

**ただし、旧規約のままで実害が出る箇所に限り、個別に見直す。**

## 3. 検討した選択肢

| 案 | 内容 | 採否 |
|---|---|---|
| A | **遡及しない。実害が出る箇所のみ個別に見直す** | **採用** |
| B | 規約変更のたびに既存文書・コードを全て新規約へ追随させる | 不採用 |
| C | 遡及を一切行わない（実害が出ても放置し、新規のものだけ新規約に従う） | 不採用 |

## 4. 判断根拠

### 1. AIによる開発では、遡及的な修正が際限なく広がる（最も重い根拠）

**本プロジェクトはエージェントによる開発の実証を兼ねている。**

エージェントは指示があれば既存箇所を機械的に洗い出し、修正できる。**その能力は、規約が変わるたびに全体を書き換える方向へ働く。**

機能が増えるほど過去の資産は増え、**「新しい規約に合わせて既存を整える」作業は、対象が増え続ける限り終わらない。** そして修正のたびに、動作していたものを壊す可能性が入り込む。

**人手の開発では、この作業のコストが自然な抑制になっていた。** エージェントではその抑制が働かない。**規約として明示的に禁じなければ、際限なく広がる。**

### 2. 過去の判断は、その時点の情報の下では正しい

**規約が変わったことは、過去の判断が誤っていたことを意味しない。**

`.claude/rules/documentation.md` は既にこの思想を持っている。

- 「**廃止した文書を削除せず「廃止」と明記する。** 過去の判断の経緯を残すため」（0節）
- 「**`docs/inputs/` は追記のみ。後の決定に合わせて書き換えない**」（3.6節）
- 「**ADRは追記のみ。決定を覆す場合、既存のADRを書き換えず新しいADRを起こす**」（7節）
- 「**`plan.md` は実験の実施前に書き、実施後に書き換えない**」（5節）

**本ADRは、これらと同じ原則を規約変更の場面へ適用したものである。**

### 3. 実害の有無で線を引けば、判断が再現できる

「重要なら直す」では基準にならない。**実害を次のいずれかへの影響と定義すれば、判断が個人の裁量に依らない。**

| 実害の区分 | 例 |
|---|---|
| **結果の再現性** | 旧手順に従うと実験結果が再現できなくなる |
| **機密境界** | 旧手順に従うと機密データが公開範囲へ出る |
| **安全性・完全性** | 旧手順に従うとデータの破壊・欠落が起きる |
| **規約間の衝突** | 確定文書が旧規約を指すため、それに従うと別の規約に違反する |

**ADR-009 の事例は「結果の再現性」に該当した。** `uv add` は `sudachidict-core` を `>=` で書き込む。辞書の版が変われば分かち書き結果が変わり、S-3 の決定が再現できなくなる。**乱数シードでは担保できない。**

## 5. 採用しなかった案を退けた理由

### 案B（全て追随させる）

**作業量が資産の量に比例して増え続ける。** 規約が10回変われば、そのたびに全文書を洗い直すことになる。

**より深刻なのは、変更のたびに壊す機会が生じることである。** 追随作業そのものに誤りが混入しうる。**実際、本プロジェクトでは「規約に合わせた修正」の過程で複数の不具合を作り込んでいる。** EXP-001 の S-2 では、設計書との相違4件を是正する過程で新たな相違を2件生み、レビューで2度差し戻された（`ISSUE-007`。本ADRの決定時点では `poc/topic-extraction-2025` ブランチ上にあり、`main` へは PoC フェーズ完了時にマージされる）。

**過去の記述が「その時点で正しかった」という情報も失われる。** 全て現在の規約で書き換えれば、いつ何が変わったのかが履歴からしか追えなくなる。

### 案C（実害が出ても遡及しない）

**規約間の衝突が解消されない。** 確定文書が旧規約を指したまま残れば、`CLAUDE.md` 2章の原則1 に従う実装者は旧規約に従うことになる。**どちらの規約に従っても違反になる状態が残る。**

**再現性・機密の問題は放置できない。** これらは後から取り返しがつかない。

## 6. 運用

### 判断の手順

規約を変更したとき、**既存の確定文書・コードについて次を確認する。**

1. **旧規約を引用している箇所を探す**（探索はする。修正の要否とは別）
2. 各箇所について、**旧規約のままで4節の実害に該当するかを判断する**
3. 該当する箇所**のみ**を改訂する。該当しない箇所は**据え置く**

### 立証責任は改訂する側にある

**据え置きが既定である。** 改訂を提案する側が、4節の実害に該当することを示す。

**「望ましい」「様式が揃っていない」「新しい規約のほうが良い」は根拠にならない。** これらはすべての箇所に当てはまるため、線が引けなくなる。

**根拠は、具体的な失敗経路として示す。** 「旧手順に従うと何がどうなって、何が損なわれるか」を、可能な限り実測を伴って書く。

[ADR-009](ADR-009-dependency-declaration.md) の事例では次の形で示した。

| 段階 | 内容 |
|---|---|
| 旧手順 | `uv add sudachidict-core` を実行する |
| 起きること | `>=20260723` として書き込まれる |
| **実測** | **`sudachidict-core` の版は `20260723`。日付そのものが版であり、辞書スナップショットを指す** |
| 損なわれるもの | 辞書が変われば分かち書きが変わり、語彙・TF-IDF・クラスタリング結果まで変わる |
| なぜ他で担保できないか | **乱数シードでは担保できない**（`.claude/rules/experiment-code.md` 禁止事項1 の対象外） |
| 影響範囲 | S-3 の決定を後続の全ステージが前提とする |

**この水準の根拠を示せない場合は据え置く。**

### 改訂する場合

**確定文書の改訂手順に従う**（`.claude/rules/documentation.md` 4節）。改訂履歴には次の2点を書く。

- **旧記述が当時の規約に従ったものであり、誤りではないこと**
- **なぜ追随が必要だったか**（4節のどの実害に該当するか、および上記の失敗経路）

**「規約が変わったから直した」とだけ書かない。** それでは、他の箇所を据え置いた判断が不可解になる。

### 据え置く場合

**記録を残さない。** 記述が変わらないため、残すべき差分が無い。

**ただし規約変更時に洗い出した結果は、その規約のADRへ記載する。** どの文書を確認し、どれを改訂し、どれを据え置いたかを1箇所にまとめる。**据え置いた判断の検証可能性はここで担保する。**

### 例外: 明示的な依頼

**利用者が明示的に依頼した場合は遡及してよい**（`CLAUDE.md` 2章の原則6 と同じ）。本ADRが禁じるのは**自動的・網羅的な追随**である。

## 7. 想定される結果

| 良い影響 | 悪い影響・受け入れるコスト |
|---|---|
| 規約変更のコストが資産量に比例して増えない | 文書間で記述の様式が揃わない |
| 追随作業による作り込み不具合が減る | 「なぜここだけ古いのか」を都度説明する必要がある |
| 過去の判断がその時点の記録として残る | 実害の判断を誤ると、衝突が残ったまま進む |
| エージェントによる無制限な書き換えを構造的に防げる | 実害の該当を検討する手間が規約変更のたびに生じる |

## 8. 見直す条件

1. **据え置いた箇所が原因で不具合が発生したとき**（`ISSUE` が起票されたとき）。4節の実害の定義が狭すぎた可能性があるため、区分を見直す
2. **規約変更の回数が10回を超えたとき**（現在 ADR-010）。据え置きの累積によって文書全体の整合が読み取れなくなっていないかを点検する
3. **本実装フェーズに入り、`src/` の資産が `experiments/` を上回ったとき。** 本番コードでは規約間の衝突がより広範に影響するため、実害の区分に「保守性」を加えるかを再検討する
