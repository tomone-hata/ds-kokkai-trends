# ADR-005: ローカルでのマージを禁止し、Pull Request 経由でマージする

| 項目 | 内容 |
|---|---|
| ID | ADR-005 |
| 状態 | 採用 |
| 決定日 | 2026-08-18 |
| 関連 | [ADR-003](ADR-003-branch-strategy.md)、[ADR-004](ADR-004-rule-change-via-branch.md)、`CLAUDE.md` 5章 |

## 1. 背景

[ADR-003](ADR-003-branch-strategy.md) で作業をブランチに分ける運用を定めたが、マージの方法は「`--no-ff` で `main` へマージする」とのみ記していた。
これはローカルでの `git merge` を想定した記述であり、以下の問題がある。

- **統合前に変更内容を俯瞰する機会がない。** ローカルマージは差分を確認しないまま実行できてしまう
- 統合の判断がコマンド実行の履歴にしか残らず、**なぜマージしてよいと判断したかが記録されない**
- 実務のチーム開発は Pull Request（以下 PR）を経由するのが一般的であり、**本プロジェクトが兼ねる予行演習としての価値が下がる**

## 2. 決定

**ローカルでの `git merge` による `main` への統合を禁止する。すべて PR を経由する。**

| 項目 | 内容 |
|---|---|
| 手順 | ブランチを push → PR 作成 → 差分を確認 → GitHub 上でマージ |
| マージ方法 | **Merge commit**（`--no-ff` 相当）。Squash / Rebase は使わない |
| 単独開発時 | レビュアーが自分自身でも PR を経由する。**差分を一覧で確認する強制力そのものが目的である** |
| PR本文 | 何を変更したか、なぜ変更したか、関連する `ADR-NNN` / `ISSUE-NNN` / `EXP-NNN` を記載する |

**ローカルの `main` は `origin/main` を取り込むためだけに使う。** `main` 上で作業もマージも行わない。

長命ブランチが `main` を取り込む方向（`git merge main`）はローカルで実行してよい。統合の向きが逆であり、`main` の状態を変えないため。

## 3. 検討した選択肢

| 案 | 内容 | 採否 |
|---|---|---|
| A | ローカルマージを禁止し、PR 経由に統一する | **採用** |
| B | ローカルマージを継続する（ADR-003 のまま） | 不採用 |
| C | 影響の大きい変更のみ PR、小さい変更はローカルマージ | 不採用 |

## 4. 判断根拠

1. **統合前に差分を俯瞰する強制力が生まれる。** PR の画面では変更ファイルと行単位の差分が一覧化される。ローカルマージにはこの段階がなく、意図しない変更（機密の混入、規約違反、消し忘れ）を最後に検出する機会を失う
2. **統合の判断が記録として残る。** PR の本文・コメント・マージコミットが、なぜ統合してよいと判断したかを保存する。ADR や CHANGELOG では拾えない粒度の経緯が残る
3. **実務の手順と一致する。** 本プロジェクトは実務投入の予行演習を兼ねている。チーム開発では PR が標準であり、ここでローカルマージを続けると手順が乖離する
4. **CI・自動チェックの接続点になる。** 将来テストや機密スキャンを自動化する場合、PR が実行の起点となる。先に PR 運用を確立しておけば追加が容易になる

## 5. 採用しなかった案を退けた理由

- **案B**: 判断根拠1のとおり、差分確認の機会が構造的に存在しない。単独開発では特に、自分が書いたものを自分でマージするため無検査になりやすい
- **案C**: 「影響が小さい」の判断を都度行う必要があり、その判断自体が誤りうる。**差分を確認して初めて影響の大きさが分かる**ため、確認前に手順を分岐させるのは順序が逆である

## 6. 想定される結果

| 良い影響 | 悪い影響・受け入れるコスト |
|---|---|
| 統合前に必ず差分を確認する | 手数が増える（push・PR作成・マージの3段階） |
| 統合の判断と経緯が保存される | ネットワーク接続が必要になる |
| 将来のCI導入が容易になる | |

## 7. マージ方法を Merge commit に固定する理由

Squash はブランチ内の個々のコミットを1つに潰すため、**実験や調査の過程が失われる**。
Rebase は履歴を直線化するが、**どこからどこまでが1つの作業単位だったかが判別できなくなる**。

[ADR-003](ADR-003-branch-strategy.md) が `--no-ff` を選んだ理由（作業の単位を履歴に残す）をそのまま踏襲し、Merge commit に固定する。

## 8. 見直す条件

- ネットワーク不通の環境で作業する必要が生じ、PR 経由が実行できなくなったとき
- PR の作成コストが実作業を圧迫していると判断されたとき（その場合も案Cではなく、PR作成の自動化を先に検討する）
