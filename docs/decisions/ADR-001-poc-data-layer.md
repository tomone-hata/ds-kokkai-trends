# ADR-001: PoCではRDB・Dockerを導入せず Parquet + DuckDB で完結させる

| 項目 | 内容 |
|---|---|
| ID | ADR-001 |
| 状態 | 採用 |
| 決定日 | 2026-08-18 |
| 関連 | `CLAUDE.md` 6章「データ層（PoC）」 |

## 1. 背景

本プロジェクトは最終的に2020〜2026年の国会会議録を対象とし、収集した発言と分析結果を蓄積する。
この規模を見越して、PoC段階からPostgres等のRDBを導入し、Docker化しておくべきかを判断する必要があった。

判断に先立ち、国会会議録検索APIに件数を実測した。

| 対象期間 | 発言数 |
|---|---|
| 2025-01-01〜2025-12-31（PoC対象） | 118,566 |
| 2020-01-01〜2026-12-31（本番想定） | 763,438 |

## 2. 決定

PoC段階ではRDBとDockerを導入せず、Parquet + DuckDB のファイルベースで完結させる。
Postgres と Docker の導入は本実装フェーズから行う。

## 3. 検討した選択肢

| 案 | 内容 | 採否 |
|---|---|---|
| A | Parquet + DuckDB。RDB・Dockerなし | **採用** |
| B | 最初から Docker + Postgres を構築 | 不採用 |
| C | 分析はParquetで進めつつ、docker-compose と DDL のみ先行整備 | 不採用 |

## 4. 判断根拠

1. **規模がRDBを要さない。** 本番想定の763,438発言でもParquetで数百MB規模に収まり、単一マシンで完結する。PoCでは同時アクセス制御もトランザクションも必要ない（書き手も読み手も1名、収集は追記のみ）
2. **PoCではスキーマが必ず変わる。** 発言の分割単位、短文発言の除外閾値、埋め込みモデルと次元数、クラスタ粒度はいずれも実験を経て決まる。確定前にDDLとマイグレーションを管理するコストが、RDBから得られる利点を上回る
3. **macOSではDockerがMetal/MPSにアクセスできない。** Docker Desktop for Mac はLinux VM上で動作するため、埋め込み計算をコンテナ内のCPUで回すことになり、イテレーション速度が落ちる
4. **Postgresを導入しても計算上の重い部分は解決しない。** 763,438件×768次元の埋め込み行列は約2.3GBで、クラスタリング時にアプリ側のメモリへ載せるもの。pgvectorを用いてもバッチクラスタリング自体はアプリ側で走る

## 5. 採用しなかった案を退けた理由

- **案B**: 得られるのは同時アクセス制御とトランザクションだが、PoCではいずれも不要。一方でスキーマ変更のたびにマイグレーションが発生し、判断根拠3のGPU制約も抱え込む
- **案C**: スキーマが未確定の段階でDDLを書くことになり、実験結果次第で手戻りする。先行整備の利点が出ない

## 6. 想定される結果

| 良い影響 | 悪い影響・受け入れるコスト |
|---|---|
| スキーマ変更がファイル書き換えで済み、実験の反復が速い | 本実装フェーズでPostgresへの移行作業が発生する |
| 埋め込み計算をネイティブ実行でき、MPSを利用できる | 同時アクセスが必要になった時点で構成変更が要る |

移行コストを抑えるため、以下を収集の設計時点から守る（`CLAUDE.md` 6章に規約として記載）。

1. 生データはParquet形式で保存し、APIのフィールド名をそのまま列名にする
2. `speechID` を主キーとして扱う
3. `data/raw/year=YYYY/month=MM/` の形で日付パーティションに配置する
4. 集計・分析のクエリはDuckDBのSQLとして書く

## 7. 見直す条件

**可視化アプリとしてクエリを配信し、増分更新を運用に乗せる段階に入ったとき**（本実装フェーズ）に再検討する。
それ以前でも、以下のいずれかに該当した場合は前倒しで見直す。

- 複数プロセスからの同時書き込みが必要になったとき
- 分析結果の更新履歴を保持する要件が出たとき
