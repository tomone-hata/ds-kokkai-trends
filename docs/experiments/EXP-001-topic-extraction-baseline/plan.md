## 1. 目的

国会会議録の発言を教師なし学習で「論点」に分解できるかを確かめ、**EXP-002 以降の比較基準となる測定値を得る。**

**本実験は探索的実験である。** 品質に閾値を置かず、成立性のみを撤退基準とする（要件定義書 3.3節）。

## 3. 撤退基準

**この基準に触れた場合、実験を打ち切って方針を見直す。実施後に緩めない。**

**品質（シルエット係数・解釈可能率・一致率）を撤退基準に含めない。** 品質は測定してベンチマーク化する（要件定義書 3.3節）。

### 3.1 D-1: 収集（S-1）

| # | 判定時点 | 条件 | 打ち切り時の次の手 |
|---|---|---|---|
| D-1a | 累計 **10,000件** を取得した時点 | 実測スループット（件／稼働時間）から2025年 118,566件へ外挿した稼働時間が **24時間** を超える見込み | **中断**し、`maximumRecords` と待機秒の設計を見直す。再測定でも超える場合は D-1c へ |
| D-1b | 収集完了時 | 収集プロセスの**稼働時間の累計**が **24時間** を超えて完了した | 記録のうえ継続可。ただし D-1c を必ず判定する |
| D-1c | 収集完了時 | 実測スループットから本番規模 819,428件へ外挿した稼働時間が **7日（168時間）** を超える | **撤退。** 本番運用が成立しないため、Phase 2 の収集設計を先に見直す |

**判定は暦時間ではなく稼働時間の累計で行う。** 収集は中断・再開可能に実装するため、暦時間には待機・中断が含まれる。

### 3.2 D-2: 計算資源（S-6）

| # | 条件 | 措置 |
|---|---|---|
| D-2a | 1構成のベクトル化が **6時間** を超える | 当該構成を脱落 |
| D-2b | 1構成の埋め込み処理が PoC で **4時間**／本番外挿で **24時間** を超える | 当該構成を脱落 |
| D-2c | 1構成のクラスタリングが **2時間** を超える | 当該構成を脱落 |
| D-2d | 物理メモリ使用率が **70%** を超える | 当該構成を脱落 |
| D-2e | **すべての候補構成**が D-2a〜D-2d により脱落した | **撤退** |

### 3.3 D-3: クラスタの退化（S-6）

| # | 条件 | 措置 |
|---|---|---|
| D-3a | 最大クラスタが全体の **80%以上** | 当該構成を脱落 |
| D-3b | クラスタ数が対象件数の **5%** を超える（平均サイズ20未満） | 当該構成を脱落 |
| D-3c | ノイズ点が **80%以上**（密度ベース手法の場合） | 当該構成を脱落 |
| D-3d | **すべての候補構成**が該当した | **撤退** |

### 3.4 中間判断ポイント

| # | 時点 | 判定 | 否の場合 |
|---|---|---|---|
| **CP-1** | **S-1 完了時** | D-1a / D-1b / D-1c | **S-2 以降に進まない** |
| CP-2 | S-6 の X-1 完了時 | D-2・D-3（当該構成） | 次の構成へ。全構成脱落で撤退 |
| CP-3 | S-6 完了時 | D-2e・D-3d | 撤退 |

**CP-1 を通過するまで S-2 以降に着手しない。** 収集が成立しなければ他のすべてが無意味になる。

**S-3・S-4・S-5 では撤退判定を行わない。** これらは暫定固定値での実行であり、そこでの退化は候補構成全体の退化ではない。ただし**選定のための判定には D-3 を用いてよい**（設計書 2.4節）。D-2 に触れた場合はその場でサブサンプリング（n=30,000）へ縮退し、事実を記録する。

## 5. 手順

### 5.1 ステージと順序

**段階的に決定し、決定した水準を後段で固定する（グリーディ）。全組み合わせを回さない。**

| ID | ステージ | 前提 | 想定工数 |
|---|---|---|---|
| **S-0** | 参照論点リストの作成（参照A・B） | なし。**S-1 と並行実施可** | 未見積もり（暫定1〜2日） |
| **S-1** | **データ収集** → **CP-1** | なし | 実装2日 + 実行 |
| S-2 | データ品質確認 | S-1 | 1日 |
| S-3 | 分かち書きの決定 | S-2 | 1.5日 |
| S-4 | 前処理水準の決定 | S-3 | 1日 |
| S-5 | 分析単位の決定 | S-4 | 1.5日 |
| S-6 | ベクトル化 × クラスタリング → **CP-2・CP-3** | S-5 | 3日 |
| S-7 | 主観評価（SE-B）・一致度測定・**構成の確定** | S-6 | 1.5日 |
| S-8 | 参照リストとの突合 | S-0・S-6・S-7 | 1.5日 |
| S-9 | 命名とコスト見積もり | S-7 | 1日 |
| S-10 | 時系列集計と粒度比較 | S-7 | 1日 |
| S-11 | レポート作成 | 全ステージ | 1日 |

**合計 16.0人日**（S-0 を除く）／**17.0〜18.0人日**（S-0 の暫定値を含む）。S-1 の実行時間と S-8 の再判定待機は含まない。**期限は設定しない。**

### 5.2 S-1（データ収集）の手順

| # | 手順 |
|---|---|
| 1 | **API仕様を原典で再確認**し、確認日を `config.md` に記録する |
| 2 | 出力先が `.gitignore` 対象であることをスクリプト先頭でアサートする |
| 3 | 対象期間を**月単位**に分割し、単位ごとに `from` / `until` を指定する |
| 4 | 各単位の**最初のレスポンスから期待件数（`numberOfRecords`）を取得**し、マニフェストへ記録する |
| 5 | `nextRecordPosition` を辿って全件を取得する。**1リクエストごとにリクエスト前に待機する** |
| 6 | Parquet へ保存する。**`raw_json` 列にAPIレスポンスの当該レコードをそのまま保持する** |
| 7 | **完了判定**: 取得件数が期待件数と一致し、かつ `speechID` に重複と欠損がないこと。**両方を満たす場合のみ「完了」** |
| 8 | 累計取得件数・累計リクエスト数・累計稼働時間・エラーコード別発生回数を一定間隔でログに出す |
| 9 | **累計10,000件の時点で D-1a を判定する** |
| 10 | 全単位の完了後、**CP-1（D-1b・D-1c）を判定する** |

**再実行時は完了済みの単位をスキップする。** 失敗・進行中の単位のみ再実行する。

## 6. 評価方法

教師なし学習のため正解ラベルがない。**S-1 では品質を評価しない。** 評価対象は成立性のみである。

| 観点 | 判断方法 |
|---|---|
| 収集の成立性 | D-1a・D-1b・D-1c（3.1節） |
| データの完全性 | 期待件数との一致、`speechID` の重複・欠損なし |

S-6 以降の品質測定（シルエット係数・解釈可能率・一致率・両者の一致度）は設計書 5章に定める。**いずれも閾値を置かず測定のみ行う。**

## 8. 想定される結果

**実施前の予想を書く。外れた場合にそれが発見になる。**

| # | 予想 |
|---|---|
| 1 | `maximumRecords` を上限まで使えれば、収集は **1〜2時間**で完了する（1リクエスト4秒・r=100 で約1.3時間）。24時間の撤退基準には大きな余裕がある |
| 2 | 19001（混雑）はまれにしか発生せず、リトライで吸収できる |
| 3 | 発言の文字数分布は**右に長い裾**を持つ。短文（「異議なし」等）が相当数を占める |
| 4 | `numberOfRecords` は期待どおり総件数を返し、`nextRecordPosition` によるページングで取りこぼしなく全件取得できる |

**4 は未確認である。** API仕様の要約に `numberOfRecords` の意味の記載がなく、実際に叩いて確かめる以外にない。**取りこぼしが生じた場合、完了判定（手順7）が検出する。**
