# ISSUE-006: 0件の月がスキーマを持たない Parquet として書き出され、後続の読み込みが失敗する

| 項目 | 内容 |
|---|---|
| ID | ISSUE-006 |
| 種別 | **不具合** |
| 状態 | **対応済** |
| 起票日 | 2026-08-20 |
| 解決日 | 2026-08-20 |
| 影響範囲 | `experiments/EXP-001-topic-extraction-baseline/run_01_collect.py`（S-1 データ収集）、および `data/raw/` を読む後続の全ステージ |

> 本ISSUEは実験コードの不具合である。**対策はコード修正のみで、`design/` の確定文書には影響しない**（`.claude/rules/documentation.md` 6節）。

## 1. 事象

### 観測された結果

2025年の全件収集（118,566件）は正常に完了したが、**収集したデータをまとめて読もうとすると失敗する。**

```
duckdb.InvalidInputException: Invalid Input Error: Failed to read Parquet file
'data/raw/year=2025/month=07/speech.parquet': Need at least one non-root column in the file
```

### 期待した結果

`data/raw/year=*/month=*/speech.parquet` のグロブ読み込みで、2025年の全件を単一のテーブルとして扱えること。

### 何が問題か

**2025年7月は該当する発言が0件であり、この月の Parquet が「列を1つも持たないファイル」として書き出された。**

| 項目 | 値 |
|---|---|
| ファイルサイズ | 176 バイト |
| 行数 | 0 |
| **列数** | **0** |

Parquet は行数0でもスキーマを持てるが、**空のレコード列からスキーマを推論することはできない。** 該当箇所は次のとおり。

```python
pq.write_table(pa.Table.from_pylist(rows), part / "speech.parquet", compression="zstd")
```

`rows` が空リストのとき `pa.Table.from_pylist([])` は**0行0列**の表を返す。この結果、他の月と列構成が一致せず、複数ファイルをまとめて読む処理が破綻する。

### 再現手順

該当月を含めて収集したうえで、次を実行する。

```bash
uv run python -c "
import duckdb
duckdb.connect().execute(
    \"SELECT COUNT(*) FROM read_parquet('data/raw/year=*/month=*/speech.parquet')\"
).fetchall()"
```

再現性: **確実に再現する**（データ依存ではなく、0件の月が存在すれば必ず起きる）。

## 2. 影響

### 収集済みデータへの影響はない

**7月以外の11か月は正常に書き出されており、データの欠落・重複はない。**

| 検証項目 | 結果 |
|---|---|
| 総件数 | 118,566件（期待値と一致） |
| `speechID` のユニーク数 | 118,566（**重複0**） |
| 列数 | 24 |

**再収集は不要である。** 問題は「0件の月に空ファイルが残っていること」だけであり、これを取り除けば解消する。

### 後続ステージへの影響は大きい

**S-2 以降のすべてのステージが `data/raw/` を読む。** 発見が S-2 の着手時であったため実害は出ていないが、**この不具合は「収集は成功したように見えるのに、データが使えない」という形で現れる。** マニフェストは全単位「完了」を示し、件数も一致するため、**収集ログだけを見ても気づけない。**

### 本番規模ではより起きやすい

PoC は2025年の12か月で、0件の月は1つ（7月）だった。**本番は2019〜2025年の84か月であり、閉会期間に該当する月がより多く現れる。**

## 3. 原因

**空の入力に対する分岐を置いていなかった。**

`plan.md` 8節「想定される結果」は件数の多寡を予想しているが、**「0件の月がありうる」ことを想定していない。** 国会には閉会期間があるため0件の月は制度上ありうるが、収集スクリプトの設計時にこれを考慮していなかった。

**完了判定は正しく動作していた。**

```python
ok = (got == expected) and (dup == 0)
```

期待値0・取得0・重複0であるため `ok` は真となる。**判定ロジックの誤りではなく、判定を通過した後の書き出しの問題である。**

## 4. 対策

**0件の場合はファイルを書き出さない。**

```python
if rows:
    part = RAW_DIR / f"year={unit_from.year}" / f"month={unit_from.month:02d}"
    part.mkdir(parents=True, exist_ok=True)
    pq.write_table(pa.Table.from_pylist(rows), part / "speech.parquet", compression="zstd")
else:
    log.info("[%s] 該当0件のためファイルを作成しない", key)
```

### なぜ「空でもスキーマを付けて書く」ではないのか

スキーマを明示すれば0行0列は避けられるが、**そのためには列定義をコード中に固定する必要がある。**

これは [ADR-001](../../decisions/ADR-001-poc-data-layer.md) 6.1節の「生データは可逆に保存する」方針と衝突する。現在の実装は `pa.Table.from_pylist` によってレスポンスの構造をそのまま受け取っており、**列定義を持たないことが、API の仕様変更に対して壊れにくいという性質を生んでいる。** ここで列を固定すると、その性質を失う。

**0件の月は「データが無い」のであって「空のデータがある」のではない。** ファイルを作らないことが事象に忠実である。Hive パーティションは存在しないパーティションを単に読み飛ばすため、後続の読み込みに支障はない。

### 既存の空ファイルの扱い

**`data/raw/year=2025/month=07/` を削除する。** 再収集は不要（マニフェストは完了済みのままでよく、0件であることは記録されている）。

## 6. 再発防止

**「正常に完了した」と「結果が使える」は別である。**

本件は収集スクリプトの完了判定・マニフェスト・ログのすべてが正常を示す状態で発生した。**実行の成否ではなく、成果物そのものを検証しなければ検出できない。**

したがって S-1 の完了条件に次を加える（`config.md` に実測値を記録する）。

| # | 検証項目 |
|---|---|
| 1 | `data/raw/` 全体をグロブで読み込めること |
| 2 | 総件数が期待値と一致すること |
| 3 | `speechID` に重複がないこと |
| 4 | 全パーティションで列構成が一致すること |

**この4項目は本番実装でも引き継ぐ。** 境界値（0件、1件）は実データで初めて現れるため、設計段階では見落とされやすい。
