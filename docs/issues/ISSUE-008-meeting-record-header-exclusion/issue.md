## 1. 事象

**`speechOrder = 0` のレコードが 1,126件存在し、これらは発言ではない。**

| 判定根拠 | 値 |
|---|---|
| **`speaker` 列の値** | **全1,126件が「会議録情報」** |
| 件数と会議数（`issueID` のユニーク数）の一致 | 1,126 = 1,126（**1会議あたり厳密に1件**） |
| `○`（発言開始記号）で始まらない唯一のレコード群 | 該当 |

**API 自身が発言者ではないと表示している。** 発言に付与される `○` も持たない。

### 記載されている内容

**会議録の front matter（冒頭情報）である。** 内容の出現率は次のとおり。

| 要素 | 出現率 |
|---|---|
| 開催日・開会時刻 | 100% |
| **本日の会議に付した案件** | 99.9% |
| 委員長名 | 89.3% |
| **政府参考人名簿** | 48.5% |
| **出席委員名簿** | 48.0% |
| 議事日程 | 7.4% |
| 委員の異動（辞任・補欠選任） | — |

平均81行・中央値71行で、**大半が氏名の羅列である。**

| 指標 | 値 |
|---|---|
| 「君」（名簿行の人名後置語）の出現回数 平均 | **67.8** |
| 同 最大 | **1,703** |

**1レコードあたり平均約68名分、最大で約1,700名分の氏名を含む。**

## 2. 影響

### 統計を歪めている

| 統計量 | 全118,566件 | `speechOrder = 0` を除く（117,440件） |
|---|---|---|
| 平均 | 415.8 | **403.2** |
| 中央値 | 318.0 | 314.0 |
| p99 | 2,220.4 | **2,020.6** |
| **最大** | **46,976** | **16,547** |

| 項目 | 値 |
|---|---|
| 件数の割合 | 0.95% |
| **総文字数に占める割合** | **3.96%**（1,951,554 / 49,299,337 文字） |
| 当該レコードの平均文字数 | 1,733.2 |

**`config.md` が Q-3・Q-7 で「最大 46,976」と記録した値は発言ではない。** 10,000字以上のレコード13件のうち4件がこれに該当し、その平均は 23,304字である。

### 設計書に除外する工程が無い

6.1節の処理順序は次のとおりで、**このレコードを取り除く工程が存在しない。**

| 順 | 処理 |
|---|---|
| 1 | `speechID` による重複除去 |
| 2 | 対象期間による絞り込み |
| 3 | テキストの正規化 |
| 4 | 短文発言の除外 |
| 4A | 分析単位の構成 |

**工程4（短文発言の除外）では落ちない。** 平均1,733字であり、下限の閾値には掛からない。**長い側の裾に残り続ける。**

### 後続ステージへの影響

**6.4節が測定項目として挙げる「(a) 文字数の分布と上位側の裾の重さ」「(c) 最長級の発言10件の目視確認」は、現状のままだと会議録の冒頭情報を対象にすることになる。**

クラスタリング（S-6）では、**氏名の羅列が独自のクラスタを形成しうる。** それは論点ではない。

## 3. 原因

**設計時に、API のレスポンスに発言以外のレコードが含まれることを想定していなかった。**

[`docs/inputs/kokkai-api-spec-summary.md`](../../inputs/kokkai-api-spec-summary.md) は `speech` エンドポイントを「**ヒットした発言の本文**＋所属する会議録の情報」と記載しており、公式仕様にも「発言以外のレコードが返る」旨の記載はない。

同文書の「この仕様書から分からないこと」節が述べるとおり、**実データを見なければ分からない事項であった。** S-2（データ品質確認）はまさにこれを検出するためのステージであり、**検出自体は想定どおりに機能した。**

## 4. 対策

### 4.1 設計書 6.1節に工程を追加する

**工程2の後、工程3（正規化）の前に、会議録冒頭情報の除外を置く。**

| 順 | 処理 | 備考 |
|---|---|---|
| 2 | 対象期間による絞り込み | |
| **2A** | **会議録冒頭情報の除外**（`speechOrder = 0`） | **新規。除外件数をアサートする** |
| 3 | テキストの正規化 | |
| 4 | 短文発言の除外 | |

**正規化より前に置く理由。** このレコードは発言ではないため、話者表記の除去（3-3）やト書きの除去の対象にならない。**正規化の対象に含めると、除去パターンの設計が冒頭情報の書式に引きずられる。**

**判定条件は `speechOrder = 0` とする。** `speaker = '会議録情報'` でも同一の集合が得られるが、**`speechOrder` は数値であり表記揺れの影響を受けない。** ただし両者が一致することを S-2 で確認し、**アサーションとして残す**（一致しなくなった場合は API 側の変化を示す）。

### 4.2 「除外」であって「削除」ではない

**生データ（`data/raw/`）からは削除しない。** `raw_json` 列を含めて可逆に保存されており（[ADR-001](../../decisions/ADR-001-poc-data-layer.md) 6.1節）、除外は分析パイプライン上の工程である。

**今後の分析で利用しうる情報を含むため、この区別は重要である。**

| 含まれる情報 | 想定される用途 |
|---|---|
| **本日の会議に付した案件**（99.9%） | 議題そのもの。参照論点リスト（S-0）の補強、クラスタと議題の突合 |
| 出席委員・政府参考人の名簿 | 会議の性格の分類、府省庁の関与の把握 |
| 委員の異動 | 会期中の構成変化の追跡 |
| 開会・散会時刻 | 会議の規模の代理指標 |

**Phase 2 以降で使う可能性がある。** 本ISSUEが決めるのは「EXP-001 の論点抽出パイプラインに乗せない」ことのみである。

### 4.3 機密の扱い

**このレコードは発言本文より個人情報の密度が高い。** 1件あたり平均約68名分の氏名を含む。

`CLAUDE.md` 3章の境界（**生の発言と話者を出さない**）に照らし、**`docs/` へ内容を転記しない。** 本ISSUEに記載しているのは出現率・件数・統計値（集計値）のみである。

**分析対象から外すことは、機密の観点からも望ましい。** 論点抽出に必要のない氏名の塊を、ベクトル化や外部LLMへの送信の経路に乗せない。

## 6. 再発防止

**外部APIのレスポンスに、意味の異なるレコードが混在しうることを前提に設計する。** 公式仕様が「発言の本文を返す」と記載していても、**1レコード = 1発言とは限らない。**

**件数の一致は強い手がかりになる。** 本件は「1,126件が会議数と完全に一致する」ことから、1会議あたり1件の付随レコードであると特定できた。**分布の異常値を見たら、件数が他の集計軸と一致しないかを確認する。**

**最大値・最小値のレコードが何であるかを必ず確認する。** 統計量だけを見ていると、分布の端に別種のレコードが混じっていても気づかない。設計書 6.4節 (c) が「最長級の発言10件の目視確認」を求めているのはこのためであり、**S-2 の時点で実施していれば早期に検出できた。**
