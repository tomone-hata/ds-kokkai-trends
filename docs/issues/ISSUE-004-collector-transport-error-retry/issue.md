## 1. 事象

### 観測された結果

2025年の全件収集を実行したところ、**約46分・869リクエスト・86,741件を取得した時点で例外により停止した。**

```
httpx.RemoteProtocolError: Server disconnected without sending a response.
```

### 期待した結果

2025年の全12か月を収集し、CP-1（D-1b・D-1c）の判定まで到達すること。

### 何が問題か

**リトライ対象を `BusyError`（APIエラー19001）のみに限定しており、トランスポート層の失敗を想定していなかった。** 接続が切れた時点で例外が伝播し、収集全体が停止する。

`CLAUDE.md` 0章および設計書 3.2節 #4 は「リトライしてよいのはエラー19001（混雑）のみ」と定めるが、**これは API のエラーコードについての規定である。** 19004〜19020 は検索条件の誤りであり、同じ要求を再送しても決定的に失敗する。一方**接続断は一過性であり、性質が異なる。**

### 再現手順

```bash
uv run python experiments/EXP-001-topic-extraction-baseline/run_01_collect.py \
    --from 2025-01-01 --until 2025-12-31
```

再現性: **1回のみ観測**（同一実行内でスタックトレース中に3回出現するが、これは1つの例外の連鎖である）。**再現性は未確認。**

### 停止時点の状態

| 項目 | 値 |
|---|---|
| 実行時間 | 10:19:37 〜 11:05:35（約46分） |
| リクエスト数 | 869 |
| 完了した単位 | 2025年1月〜5月（**85,141件**） |
| 中断した単位 | 2025年6月（`startRecord=2401`。期待11,887件に対し取得0件） |
| 19001（混雑）の発生 | **0回** |

**データの整合性は保たれている。** Parquet は単位（月）の完了時にのみ書き込むため、6月の部分データは存在しない。マニフェストで6月は「進行中」であり、再実行時に6月から再開される。

## 2. 調査ログ

**追記のみ。否定された仮説も消さない。**

### 2026-08-20

- **確認したこと**: ログ全体、マニフェスト、`data/raw/` の実体
- **結果**: 1〜5月の5単位が完了し、Parquet も5つ存在する。6月の Parquet は存在しない。**部分書き込みによる不整合は発生していない**
- **確認したこと**: 停止直前のリクエスト間隔（11:05:26 → 11:05:29 → 11:05:32）
- **結果**: **3秒間隔で規則的に発行されている。** 設定した `WAIT_SECONDS=3.0` どおりであり、多重リクエストや間隔の詰まりは起きていない
- **確認したこと**: `D-1a` の判定結果
- **結果**: 実測 125,277件/時、2025年への外挿 **0.95時間**（閾値24時間）。**通過している。** 収集の成立性（H-001）そのものは肯定的である

### 原因の候補（2026-08-20 時点）

| # | 仮説 | 根拠 | 状態 |
|---|---|---|---|
| A | **keep-alive 接続の再利用競合。** サーバが閉じた接続を `httpx.Client` が再利用しようとした | `httpx` は既定で接続を再利用する。「応答なしに切断」はこの競合の典型的な症状である。**HTTPステータスもAPIエラーコードも返っていない**ことと整合する | **有力** |
| B | **提供元によるアクセス遮断。** 46分間の連続アクセスを負荷と判断された | 公式ページに「安定運用に支障をきたすと当館が判断した場合には、予告なくアクセスを遮断する等の措置をとることがあります」との記載がある | **排除できない** |
| C | ネットワーク経路上の一過性障害 | — | 排除できない |

**AとBを症状から区別できない。** いずれも「応答なしの切断」として現れる。

- **否定した仮説**: 「リクエスト間隔が短すぎた」。実測3秒間隔であり、公式ページの「数秒程度空けて」を満たしている。また19001（混雑）が1回も発生しておらず、サーバ側が過負荷を認識した形跡がない

## 3. 原因

**直接の原因は実装の不備である。** リトライ対象を API エラーコード19001のみに限定し、トランスポート層の例外を扱っていなかった。

**切断そのものの原因は未特定である**（仮説A・B・Cを区別できていない）。

## 4. 対策

| 項目 | 内容 |
|---|---|
| 選択した対策 | **コード修正のみ。** 設計変更を伴わない |
| 恒久対策か暫定対応か | **暫定対応を含む。** 切断の原因が未特定であるため、仮説A・Bの双方に耐える形にする |

### 4.1 トランスポート層のエラーをリトライ対象に加える

`httpx.TransportError`（`RemoteProtocolError`・`ConnectError`・`ReadTimeout` 等の基底クラス）を、19001 とは**別系統**のリトライ対象とする。

**規約の趣旨は維持される。** 「リトライしてよいのは19001のみ」が禁じているのは、**決定的に失敗する要求の再送**（検索条件の誤り）である。接続断は要求の内容に起因しない。

### 4.2 バックオフを長めに取る

仮説B（アクセス遮断）であった場合、短間隔での再試行は状況を悪化させる。**待機を長めに設定する**（最小30秒・最大600秒）。

- 仮説Aであれば、1回目の再試行で新しい接続が張られ即座に回復する（待機は無駄になるが害はない）
- 仮説Bであれば、間を空けることで回復する可能性がある。回復しなければ**繰り返し失敗して顕在化する**

### 4.3 接続エラーの発生回数を19001と分けて記録する

マニフェストに `transport` として別カウントする。**再発の頻度が分かれば、仮説AとBを事後に切り分けられる。**

### 4.4 リトライ上限に達した場合の扱い

**リトライ上限に達したら停止する。** 無制限に再試行しない。提供元への負荷を避けるためである。停止しても完了済みの単位は保持され、再実行で再開できる。

## 6. 再発防止

**外部APIを呼ぶコードでは、APIのエラー応答とトランスポート層の失敗を別に扱う。** 両者は性質が異なり、前者は要求の内容に起因し、後者は起因しない。

`.claude/rules/production-code.md` 9章は「リトライ（Exponential Backoff）とタイムアウトを必ず実装する」と定めるが、**リトライ対象の分類までは規定していない。** 本番コードの実装時に、この区別を設計へ反映すること。

**原因が未特定のまま対策を打つ場合、どの仮説に対する対策かを記録する。** 本件では仮説A（keep-alive競合）と仮説B（アクセス遮断）を区別できないため、双方に耐える設計とした。**再発時にこの記録がなければ、同じ切り分けをやり直すことになる。**
