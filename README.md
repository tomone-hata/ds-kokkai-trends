# データサイエンス案件テンプレート（Claude Code）

データ分析・機械学習案件を、**要件定義から本番検証まで一貫した文書の連鎖として進める**ためのテンプレートです。

各工程を担当するサブエージェントと、ディレクトリごとに切り替わるコード規約がセットになっています。このフォルダをコピーして使い、案件に合わせてエージェントを追加・削除してください。

---

## 1. 設計思想

このテンプレートは3つの前提の上に成り立っています。ここを外すと個々のエージェントが機能しません。

### 前提1: 各工程は「前工程の文書を読み、次工程の文書を書く」

```
要望テキスト
  → 分析要件定義書 → PoC設計書 → 実験レポート
  → アルゴリズム設計書 → システム設計書 → 実装 → 検証レポート
```

エージェントは役割名ではなく「**どの文書を食べて、どの文書を吐くか**」で定義されています。この鎖が繋がっている限り、各エージェントは前工程の成果物だけを読めば動きます。

### 前提2: 作った本人に採点させない

実験を実行したセッションに結果を評価させると、意図したことを基準に採点します。実装したセッションに検証させると同じことが起きます。検証系のエージェントは、別コンテキストで成果物だけを読んで判定します。

### 前提3: 規約はディレクトリで切り替える

実験コードはハードコード可、本番コードは不可。この矛盾するルールを同居させると、Claudeはどちらかを恣意的に選びます。物理的に分離し、扱うファイルの場所で自動的に切り替わるようにしています。

## 2. 使い方

```bash
cp -r ds-project-template/ your-project/
cd your-project/
git init
```

### 初期設定（3ステップ）

**1. `CLAUDE.md` のプレースホルダを埋める**

- 第0章: プロジェクトの目的、現在のフェーズ
- 第4章: データレジデンシー制約 — **該当しなければ節ごと削除**
- 第6章: 実行コマンド（`uv` 以外を使う場合は書き換え）

**2. 不要なエージェントを削除する**

すべての案件で6つ全部が要るわけではありません。単発の分析なら `system-designer` と `system-verifier` は不要です。

**3. `~/.claude/settings.json` に `.env` の読み取り拒否を設定する**

```json
{ "permissions": { "deny": ["Read(./.env)", "Read(./.env.*)"] } }
```

グローバル設定なのでリポジトリには含まれません。環境ごとに手動で設定してください。

### 動作確認

Claude Code を起動し、以下を確認します。

- `/agents` — 6つのエージェントが認識されているか
- `/memory` — `CLAUDE.md` が読み込まれているか
- `/context` — コンテキストの内訳

### 公開・非公開の境界

**`docs/` 配下は全て公開可能なものに限る。** 国会会議録APIから取得したデータは**機密データとして扱い**、`data/` と `private/` にのみ置く（[ADR-002](docs/decisions/ADR-002-public-private-boundary.md)）。

出典は公開情報だが、顧客アンケートの自由記述や社内機密データを扱う案件と手順を揃えるため、意図的に厳しい側で運用する。

境界は「**生の発言と話者を出さない**」に置く。

| 区分 | 該当するもの | `docs/` への記載 |
|---|---|---|
| 生の発言と話者 | 発言本文、発言者名、`speechID` / `issueID` | 禁止（引用も不可） |
| 集計軸 | 開催日、院名、会議名、国会回次、号数、所属会派、肩書き | 集計した形でのみ可 |
| 集計値 | 件数、統計値、クラスタ数・サイズ、時系列の推移、特徴語 | 可 |

**集計軸を個票と結びつけて書かない。** 単独では個人を指さない値でも、組み合わせると特定できる（例: 開催日＋肩書き）。

## 4. エージェント一覧

| エージェント | 入力 | 出力 | 役割 |
|---|---|---|---|
| `requirements-writer` | 要望テキスト（乱文） | `docs/requirements/` | 要望を分析要件定義書に変換。実現可能性をA/B/Cで初期判定 |
| `analysis-designer` | 要件定義書／実験レポート | `docs/design/` | **モードA**: PoC設計（撤退基準の定義）<br>**モードB**: アルゴリズム本設計（実験との差分明示） |
| `experiment-analyst` | 実験の出力 | `docs/experiments/` | 精度の健全性を検証し考察。Go/No-Go判定 |
| `system-designer` | アルゴリズム設計書 | `docs/design/` | DB・API・パイプライン・監視・障害設計 |
| `deliverable-reviewer` | 任意の成果物＋その上流 | `docs/reviews/` | 工程間の整合をレビュー。承認/条件付き/差し戻し |
| `system-verifier` | 実装コード＋設計書 | `docs/verification/` | 実際に動かして検証。リリース判定 |

### 検証系3エージェントの境界

役割が重ならないよう、見るものを明確に分けています。

| エージェント | 見るもの | 実行 |
|---|---|---|
| `experiment-analyst` | 実験結果の**数値の妥当性**と考察 | する（追加集計） |
| `deliverable-reviewer` | 成果物**どうしのリンク**（静的整合） | しない |
| `system-verifier` | システムが**設計どおり動くか** | する |

## 5. ワークフロー

```
  要望テキスト
      │
      ▼
  requirements-writer ──▶ 分析要件定義書 ──▶ deliverable-reviewer (R1)
      │
      ▼
  analysis-designer:A ──▶ PoC設計書 ──▶ deliverable-reviewer (R2)
      │
      ▼
  実験実装・実行（experiments/）
      │
      ▼
  experiment-analyst ──▶ 実験レポート ──▶ deliverable-reviewer (R3)
      │
      ├─ No-Go ──▶ analysis-designer:A（次サイクルへ）
      ▼ Go
  analysis-designer:B ──▶ アルゴリズム設計書 ──▶ deliverable-reviewer (R4)
      │
      ▼
  system-designer ──▶ システム設計書 ──▶ deliverable-reviewer (R5)
      │          ▲
      │          └── 差し戻し（精度に影響する変更）
      ▼
  実装（src/・テストファースト）──▶ deliverable-reviewer (R6)
      │
      ▼
  system-verifier ──▶ 検証レポート ──▶ リリース判定
```

### 呼び出し方

エージェントは名前で指定するのが確実です。

```
requirements-writer で、この打合せメモから要件定義書を作って
（メモを貼り付け）

experiment-analyst で exp004 の結果を見て

deliverable-reviewer で、アルゴリズム設計書を R4 モードでレビューして
```

レビューは**フェーズ完了ごとに手動で呼ぶ**運用です。実行漏れを防ぎたい場合は、`docs/PROJECT_STATUS.md` のフェーズ進捗表にレビュー判定の列があるので、そこを埋める運用にすると抜けに気づけます。

## 6. コード規約

`.claude/rules/` の各ファイルは、`paths:` フロントマターで適用範囲が決まっています。Claudeが対象ディレクトリのファイルを読んだ時点で読み込まれます。

| ファイル | 適用範囲 | 要点 |
|---|---|---|
| `experiment-code.md` | `experiments/`, `notebooks/` | ハードコード可。ただし**実行条件の記録は必須**。禁止は7項目のみ |
| `production-code.md` | `src/`, `scripts/` | ハードコード禁止。fit/transform分離。例外処理の明示 |
| `testing.md` | `src/`, `tests/` | テストファースト。**テストを実装に合わせて書き換えない** |

`CLAUDE.md` には、規約が読み込まれていなくても効くべき「全体で不変の原則」6項目だけを置いています。

## 7. カスタマイズ

### エージェントを削除する

`.claude/agents/` から該当ファイルを削除するだけです。ただし他のエージェント本文に参照が残るので、削除したエージェント名を `grep` して該当箇所を調整してください。

```bash
grep -rn "system-verifier" .claude/ CLAUDE.md
```

**案件規模別の目安**

| 案件 | 残すもの |
|---|---|
| 単発の分析・レポート納品 | `requirements-writer`, `analysis-designer`, `experiment-analyst`, `deliverable-reviewer` |
| PoCまで | 上記 ＋ 撤退基準の運用を重視 |
| 本番投入あり | 全6つ |

### エージェントを追加する

既存ファイルの構造に揃えると、他と一貫した振る舞いになります。

```markdown
---
name: エージェント名（ファイル名と一致させる）
description: いつ呼ばれるべきか。他エージェントと文面が似すぎると誤爆する
tools: Read, Write, Glob, Grep    # 必要最小限に
model: opus                        # 判断の質が要るものだけ
---

# 役割
# スコープ境界        ← 扱う / 扱わない を明記。担当外は他エージェントへ回す
# 入力                ← どの文書を読むか
# 最重要原則          ← 3〜7項目。「やりがちな失敗」を潰す形で書く
# 処理手順
# 出力（テンプレート） ← 出力先パスとフォーマット
# 完了時の報告        ← 親セッションに何を返すか
```

**追加時の注意**

- `description` が既存と似すぎると、親セッションがどちらを呼ぶか迷います。1つの文書チェーンにつき1エージェントを原則にしてください
- 実装作業をサブエージェント化しないでください。サブエージェントは親に**サマリしか返さない**ため、差分が見えず修正指示が出せません。実装は主セッションで行い、規約（`.claude/rules/`）で品質を担保する設計になっています
- 検証系を追加する場合、**対象を変更させない**指示を必ず入れてください。検証者が実装に手を入れると独立性が消えます

### 規約を変更する

`.claude/rules/` を編集します。既存コードへの遡及適用はしない方針（`CLAUDE.md` 第2章6項）なので、規約変更後にリポジトリ全体がリファクタリングされることはありません。

## 8. 未実装

`algorithm-verifier`（実装が実験と同じ数値を出すかの照合）は含まれていません。

役割としては、アルゴリズム設計書の「実験との一致確認項目」に基づき、照合用データセットに同じ入力を通して数値を突き合わせるだけの狭いエージェントです。`deliverable-reviewer` の R6 が静的整合を、`system-verifier` が動作を見るので、残るのは数値照合のみになります。

当面は `tests/golden/` のゴールデンテストで代替できます。必要になった時点で追加してください。

## 9. 既知の注意点

### パススコープの挙動にバージョン差がある

`.claude/rules/` のパススコープには報告されている不具合があります。導入後に `/memory` で実際の読み込み状況を確認してください。

- `paths:` が効かない場合、`globs: src/**, scripts/**` の形式を試す
- どうしても安定しない場合は、`CLAUDE.md` から `@.claude/rules/xxx.md` で import する（常時読み込みになりコンテキストは消費するが確実）
- ユーザーレベル（`~/.claude/rules/`）のパススコープは無視されるとの報告があるため、プロジェクトレベルに置く

### 新規ファイル作成時に規約が読み込まれない

パススコープは「そのパスのファイルを読んだとき」に発火します。新規ファイルの作成時は、まだそのファイルが存在しないため規約が効いていないことがあります。

テストファーストでは新規テストファイルの作成から始まるため、これは実際に起こります。対策として `CLAUDE.md` 第2章に不変原則を置いていますが、重要な作業の前には該当ルールを明示的に読ませるのが確実です。

### `CLAUDE.md` を肥大化させない

全セッションで読まれるため、長くなるほど個々の指示の遵守率が下がります。150行以内を目安にしてください。設計内容・障害番号・進捗は `docs/` 側のインデックスへ。

### エージェントの出力は必ず人間が読む

各エージェントは「未確定事項」「未検証項目」「判定不能」の欄を必ず埋めるよう設計されています。ここが空で出てきたら、報告を疑ってください。すべてを確認できることは通常ありません。
